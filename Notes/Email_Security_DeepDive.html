01 — إطار سياسة المُرسِلSender Policy Framework

SPF — Sender Policy Framework

SPF — Sender Policy Framework

SPF هو بروتوكول مصادقة يُحدد أي خوادم البريد مسموح لها بإرسال رسائل بريد إلكتروني باسم نطاق معين. يعمل عبر سجلات DNS ويمنع انتحال عناوين المُرسِل.

SPF is an email authentication protocol that specifies which mail servers are authorized to send email on behalf of a domain. It works via DNS records and prevents sender address spoofing.

Arabic / العربية

ما هو SPF بالضبط؟

SPF (Sender Policy Framework) هو معيار مُعرَّف في RFC 7208. يعمل كـ "قائمة بيضاء" في DNS تُخبر خوادم البريد المستقبِلة: "هذه الخوادم فقط مسموح لها بإرسال البريد من نطاقي".

عندما يستقبل خادم بريد رسالة، يسأل: "هل عنوان IP الذي أرسل هذه الرسالة موجود في سجل SPF لنطاق المُرسِل؟" إذا لم يكن — قد ترفض الرسالة أو تُصنَّف كإسبام.

المشكلة التي يحلها: أي شخص يمكنه تقنياً إرسال بريد بعنوان مُرسِل مزيف (spoofed). SPF يجعل ذلك قابلاً للاكتشاف.

English

What exactly is SPF?

SPF (Sender Policy Framework) is a standard defined in RFC 7208. It acts as a DNS-based "whitelist" telling receiving mail servers: "Only these servers are allowed to send mail from my domain".

When a mail server receives a message, it asks: "Is the IP address that sent this message listed in the sender domain's SPF record?" If not — the message may be rejected or spam-classified.

Problem it solves: Anyone can technically send email with a forged sender address. SPF makes this detectable.

⚠ SPF Limitation — يقتصر على Envelope From SPF يتحقق فقط من عنوان MAIL FROM في بروتوكول SMTP (envelope sender)، وليس من عنوان "From:" الذي يراه المستخدم في برنامج البريد! لهذا يمكن للمهاجم اجتياز SPF بينما يُظهر عنواناً مزيفاً للمستخدم — وهذا ما يُعرف بهجوم Header From Spoofing. Example 3 — Enterprise (Microsoft 365 + Salesforce + Mailchimp) enterprise.com IN TXT "v=spf1 include:spf.protection.outlook.com include:_spf.salesforce.com include:servers.mcsv.net ip4:198.51.100.0/28 -all" // ⚠ تحذير: كل include: يُضيف lookup — الحد الأقصى 10 DNS lookups
🔢 SPF DNS Lookup Limit — حد استعلامات DNS SPF يسمح بـ 10 استعلامات DNS فقط لتفسير السجل الواحد. كل include:, a, mx, exists, redirect يُحسب كاستعلام. تجاوز الحد = SPF PermError = يُعامَل كـ None أو Fail. SPF allows only 10 DNS lookups to resolve one record. Every include:, a, mx, exists, redirect counts as a lookup. Exceeding the limit = SPF PermError = treated as None or Fail.
02 — البريد المُعرَّف بمفاتيح النطاقDomainKeys Identified Mail

DKIM — DomainKeys Identified Mail

DKIM يُضيف توقيعاً رقمياً مشفراً لكل بريد إلكتروني صادر، مما يسمح لخادم الاستقبال بالتحقق من أن الرسالة أُرسِلت فعلاً من النطاق المُدّعى وأن محتواها لم يُعدَّل أثناء الإرسال.

DKIM adds a cryptographic digital signature to every outgoing email, allowing the receiving server to verify that the message was genuinely sent from the claimed domain and that its content was not modified in transit.

Arabic / كيف يعمل DKIM

مبدأ عمل DKIM — التشفير غير المتماثل

DKIM يستخدم زوج مفاتيح RSA أو Ed25519: المفتاح الخاص (Private Key) محفوظ بشكل آمن على خادم البريد الصادر، ويُستخدم لإنشاء التوقيع. المفتاح العام (Public Key) منشور في DNS ليتمكن أي خادم استقبال من التحقق.

الخادم الصادر يحسب "بصمة رقمية" (hash) لأجزاء محددة من الرسالة (headers + body)، ثم يُشفرها بالمفتاح الخاص، ويضع التوقيع في header خاص اسمه DKIM-Signature.

الخادم المستقبِل يُحمّل المفتاح العام من DNS، يُفك تشفير التوقيع، ويقارن الـ hash. تطابق = لم تُعدَّل + صادرة فعلاً من النطاق المُدّعى.

English — How DKIM Works

DKIM Principle — Asymmetric Cryptography

DKIM uses an RSA or Ed25519 key pair: the Private Key is stored securely on the outgoing mail server and used to create the signature. The Public Key is published in DNS so any receiving server can verify.

The outgoing server computes a cryptographic hash of specific message parts (selected headers + body), encrypts it with the private key, and places the signature in a special header called DKIM-Signature.

The receiving server fetches the public key from DNS, decrypts the signature, and compares the hash. Match = not tampered + genuinely from the claimed domain.

✅ DKIM vs SPF — الفرق الجوهري SPF يتحقق من مصدر الإرسال (من أي خادم؟). DKIM يتحقق من هوية المُرسِل وسلامة المحتوى (هل الرسالة أصيلة وغير معدّلة؟). DKIM يبقى صالحاً حتى بعد إعادة توجيه البريد، بينما SPF يفشل عادةً عند إعادة التوجيه. SPF verifies the sending source (from which server?). DKIM verifies sender identity and content integrity (is the message authentic and unmodified?). DKIM survives email forwarding, while SPF typically fails after forwarding.
03 — مصادقة وإبلاغ وتوافق الرسائل المستندة إلى النطاقDomain-based Message Authentication

DMARC — المظلة الجامعة

DMARC يجمع SPF وDKIM معاً ويُضيف سياسة واضحة: ماذا يفعل الخادم المستقبِل إذا فشل كلا البروتوكولين؟ كما يُرسِل تقارير تفصيلية للمالك عن كل رسالة تدّعي كونها من نطاقه.

DMARC ties SPF and DKIM together and adds a clear policy: what should the receiving server do if both protocols fail? It also sends detailed reports to the domain owner about every message claiming to be from their domain.

DMARC DNS TXT Record — _dmarc.example.com _dmarc.example.com IN TXT "v=DMARC1; p=quarantine; // السياسة: quarantine (تحجير) sp=reject; // سياسة النطاقات الفرعية: رفض pct=100; // تطبيق على 100% من الرسائل adkim=s; // تطابق DKIM صارم (strict) aspf=r; // تطابق SPF مرن (relaxed) rua=mailto:dmarc@example.com; // تقارير مجمّعة ruf=mailto:forensic@example.com; // تقارير جنائية fo=1" // إرسال تقرير عند أي فشل
السياسةPolicy (p=)الإجراءActionالاستخدامUse Case
noneلا إجراء — فقط مراقبة وتقاريرNo action — monitor only, reports sentللبدء وجمع البيانات قبل التشديدFor initial deployment and data gathering before enforcement
quarantineإرسال إلى مجلد الإسبام/الجيمSend to spam/junk folderعند التأكد من شرعية رسائلك ولكن بحذرWhen confident in legitimate mail but still cautious
rejectرفض الرسالة كلياً (SMTP bounce)Outright reject at SMTP levelالهدف النهائي — أقوى حمايةUltimate goal — strongest protection
🔗 DMARC Alignment — مفهوم التوافق DMARC يتطلب "توافقاً" بين النطاق في From: header وبين نطاق SPF (MAIL FROM) أو نطاق DKIM (d=). بدون التوافق، يمكن للمهاجم اجتياز SPF وDKIM بنطاقاتهما الخاصة بينما يُظهر نطاقاً مختلفاً في From:. relaxed يسمح بنطاقات فرعية، strict يتطلب تطابقاً تاماً. DMARC requires "alignment" between the From: domain and the SPF domain (MAIL FROM) or DKIM domain (d=). Without alignment, an attacker could pass SPF and DKIM using their own domains while showing a different From: domain. Relaxed allows subdomain matches; strict requires exact match.
04 — بوابة أمان البريد الإلكترونيMail Security Gateway

بوابة أمان البريد — كيف تعمل داخلياً

Mail Security Gateway — Internal Workings

بوابة أمان البريد (SEG) هي نظام متخصص يجلس بين الإنترنت وخادم البريد الداخلي، ويُخضِع كل رسالة واردة وصادرة لعشرات الفحوصات الأمنية قبل التسليم.

A Secure Email Gateway (SEG) is a specialized system that sits between the internet and the internal mail server, subjecting every inbound and outbound message to dozens of security checks before delivery.

معمارية بوابة أمان البريد — خطوات المعالجةSecure Email Gateway Architecture — Processing Pipeline

شرح كل مرحلة بالتفصيل

Detailed Step-by-Step Explanation

① Connection Filtering — فلترة الاتصال① Connection Filtering

أول نقطة دفاع. البوابة تتحقق من سمعة IP المُرسِل في قوائم الحجب (RBL: Realtime Blackhole List)، SORBS، SpamHaus، Barracuda Reputation. تفحص أيضاً معدل الإرسال وتطبق تقييد السرعة. الاتصالات من IPs معروفة بالإسبام تُوقَف هنا قبل استقبال أي بريد — أوفر اقتصادياً وأسرع.First line of defense. Gateway checks sender IP reputation against Realtime Blackhole Lists (RBL), SORBS, SpamHaus, Barracuda Reputation. Also checks sending rate and applies throttling. Connections from known spam IPs are dropped here before accepting any mail — most economical and fastest.

② Authentication — المصادقة (SPF + DKIM + DMARC)② Authentication (SPF + DKIM + DMARC)

البوابة تتحقق من SPF (هل IP المُرسِل مُصرَّح به؟)، DKIM (هل التوقيع الرقمي صالح؟)، DMARC (هل يتوافق النطاق في From: مع SPF/DKIM؟). تضيف نتائج التحقق كـ Authentication-Results header في الرسالة لاستخدامها في مراحل لاحقة.Gateway verifies SPF (is sender IP authorized?), DKIM (is digital signature valid?), DMARC (does From: domain align with SPF/DKIM?). Adds check results as Authentication-Results header for use in later stages.

③ Anti-Spam Engine — محرك مكافحة الإسبام③ Anti-Spam Engine

يُحلل محتوى الرسالة باستخدام خوارزميات Bayesian، قواعد هيورستيكية، ونماذج ML. يُحسب "Spam Score" لكل رسالة. SpamAssassin مثلاً يستخدم أكثر من 1000 قاعدة. عتبة الإسبام القياسية 5 نقاط. كل قاعدة تُضيف أو تُنقص نقاطاً.Analyzes message content using Bayesian algorithms, heuristic rules, and ML models. Computes a "Spam Score" for each message. SpamAssassin for example uses 1000+ rules. Standard spam threshold is 5 points. Each rule adds or subtracts points.

④ Anti-Malware / AV — الكشف عن البرمجيات الخبيثة④ Anti-Malware / AV Scanning

فحص جميع المرفقات بمحركات AV متعددة في آنٍ واحد (multi-engine). يُقارن hash الملفات بقواعد بيانات التوقيعات. يفحص الأنواع: .exe, .docm, .xlsm, .pdf, .zip, .js, .vbs, .lnk إلخ. يستخرج محتوى الأرشيفات المضغوطة للفحص.Scans all attachments with multiple simultaneous AV engines (multi-engine). Compares file hashes against signature databases. Checks types: .exe, .docm, .xlsm, .pdf, .zip, .js, .vbs, .lnk etc. Extracts compressed archive contents for scanning.

⑤ URL Analysis & Rewriting — تحليل وإعادة كتابة الروابط⑤ URL Analysis & Rewriting

استخراج جميع URLs من جسم HTML والنص. التحقق من سمعة كل رابط في قواعد بيانات التصيد (Google Safe Browsing, SURBL, URLhaus). إعادة كتابة الروابط لتمر عبر proxy الاستعراض الآمن (Time-of-Click protection). يحمي من روابط تكون شرعية وقت الإرسال لكن تتحول لخبيثة لاحقاً.Extracts all URLs from HTML body and text. Checks each link reputation against phishing databases (Google Safe Browsing, SURBL, URLhaus). Rewrites URLs to pass through safe browsing proxy (Time-of-Click protection). Protects against links that are benign at send time but become malicious later.

⑥ Sandbox — غرفة الانفجار الآمنة⑥ Sandbox — Detonation Chamber

أقوى وأبطأ مرحلة. المرفقات المشبوهة تُفتح في بيئة معزولة (VM) ويُرصد سلوكها: هل تتصل بالإنترنت؟ هل تُنشئ processes؟ هل تُعدّل Registry؟ هل تُشفّر ملفات؟ يكتشف Zero-Day malware الذي لا يظهر في قواعد التوقيعات. يُضيف تأخيراً من ثوانٍ إلى دقائق.Most powerful and slowest stage. Suspicious attachments are opened in an isolated VM and their behavior monitored: Does it phone home? Create processes? Modify Registry? Encrypt files? Discovers Zero-Day malware not in signature databases. Adds a delay of seconds to minutes.

⑦ DLP — منع تسرب البيانات⑦ Data Loss Prevention (DLP)

يفحص الرسائل الصادرة بحثاً عن بيانات حساسة: أرقام بطاقات ائتمان (PCI-DSS)، بيانات صحية (HIPAA)، أرقام هويات، معلومات سرية. يستخدم تعبيرات منتظمة (Regex)، قواعد بيانات البصمات (fingerprinting)، وML لاكتشاف سياق البيانات الحساسة.Inspects outbound messages for sensitive data: credit card numbers (PCI-DSS), health data (HIPAA), national IDs, confidential information. Uses regular expressions, fingerprinting databases, and ML for context-aware sensitive data detection.

⑧ Anti-Phishing — مكافحة التصيد الاحتيالي⑧ Anti-Phishing & Impersonation Detection

اكتشاف انتحال الهوية (Impersonation): هل "From" يشبه مسؤولاً تنفيذياً في المؤسسة؟ تحليل النطاقات المشابهة (lookalike domains): paypa1.com vs paypal.com. اكتشاف هجمات BEC (Business Email Compromise). فحص المحتوى للإشارات التلاعبية: "طلب عاجل"، "حوّل الآن".Detects impersonation: Does "From" resemble an executive in the organization? Analyzes lookalike domains: paypa1.com vs paypal.com. Detects BEC (Business Email Compromise) attacks. Inspects content for manipulation signals: "urgent request", "wire now".

05 — جمع الآثار الجنائية للبريد الإلكترونيEmail Forensic Artifact Collection

الآثار الجنائية — أين تجدها وكيف تجمعها

Forensic Artifacts — Where to Find Them & How to Collect

في الاستجابة لحوادث البريد الإلكتروني، يجب على المحلل جمع أدلة من مصادر متعددة. كل مصدر يكشف جزءاً من الصورة الكاملة للهجوم.

In email incident response, an analyst must collect evidence from multiple sources. Each source reveals part of the complete attack picture.

١. الآثار على مستوى الخادم

06 — تحليل ترويسات البريد الإلكترونيEmail Header Deep Analysis

تحليل الترويسات — دليل كامل

Header Analysis — Complete Guide

ترويسات البريد الإلكتروني هي السجل الزمني الكامل لرحلة الرسالة من المُرسِل إلى المستقبِل. كل خادم يُضيف طبقة من الترويسات. قراءتها بشكل صحيح تكشف عن الهجمات وتُحدد الأصل الحقيقي.

Email headers are the complete chronological record of a message's journey from sender to recipient. Each server adds a layer of headers. Reading them correctly reveals attacks and identifies the true origin.

مثال ترويسة كاملة مشروحة — رسالة تصيد احتيالي

Received: headers — قراءتها من الأسفل للأعلىRead bottom to top

أحدث Received يظهر أعلاها. الأقدم (حيث بدأت الرسالة) أسفلها. كل خادم يُضيف سطر Received في الأعلى. لتحديد الـ IP الأصلية اقرأ آخر Received مضاف من مصدر خارج شبكتك الداخلية.Most recent Received is topmost. The oldest (where message originated) is at the bottom. Each server prepends a Received line. To find the originating IP, read the last Received added by a server external to your network.

← هذا أُضيف بواسطة خادمنا الداخلي Received: from mail-gateway [10.0.0.5] by mx.targetcorp.com at 09:23:41 ← هذا مصدر الرسالة الحقيقي (خارجي) Received: from smtp.evil-phishing.ru [91.108.56.22] by mail-gateway at 09:23:39 /// IP الأصلي: 91.108.56.22 — تحقق منه في threat intel

Authentication-Results — نتائج المصادقةAuth Results

ثلاثة فشول واضحة: SPF softfail (91.108.56.22 ليس في سجل nationalbank.com)، DKIM fail (لا يوجد توقيع)، DMARC fail مع إجراء quarantine. هذا وحده يُؤكد أن الرسالة ليست من nationalbank.com الحقيقي.Three clear failures: SPF softfail (91.108.56.22 not in nationalbank.com record), DKIM fail (no signature), DMARC fail with quarantine action. This alone confirms the message is NOT from the real nationalbank.com.

spf=softfail // IP المُرسِل غير مُصرَّح به في سجل nationalbank.com SPF dkim=fail reason="no signature" // لا يوجد توقيع DKIM أصلاً dmarc=fail action=quarantine // From: لا يتوافق مع SPF/DKIM

From: vs Return-Path: vs Reply-To: — التناقض المقصودIntentional Mismatch

هذا هو قلب هجوم التصيد. ثلاثة عناوين مختلفة:This is the heart of the phishing attack. Three different addresses:

From: billing@nationalbank.com ← ما يرى المستخدم (مزيف) Return-Path: billing@phishing-domain.ru ← SMTP envelope (الحقيقي) Reply-To: collect@evil-payments.com ← لو رد المستخدم يصل للمهاجم

Message-ID: — كاشف هوية الخادمServer Identity Revealer

Message-ID يُولَّد تلقائياً بواسطة خادم الإرسال. الجزء بعد @ يُظهر hostname الخادم الحقيقي. هنا: smtp.evil-phishing.ru — يتناقض مع الادعاء بأن الرسالة من nationalbank.com.Message-ID is auto-generated by the sending server. The part after @ reveals the real server hostname. Here: smtp.evil-phishing.ru — contradicts the claim to be from nationalbank.com.

Message-ID: <20240115062338.1A2B3C4D5E6F@smtp.evil-phishing.ru> /// domain بعد @ = smtp.evil-phishing.ru ≠ nationalbank.com ← تناقض

X-Mailer: — أداة الإرسالSending Tool Fingerprint

PHPMailer مكتبة PHP لإرسال البريد. تُستخدم كثيراً في حملات التصيد المبرمجة. البنوك الحقيقية لا ترسل بريدها عبر PHPMailer مباشرةً. هذا مؤشر قوي.PHPMailer is a PHP library for sending mail. Commonly used in programmatic phishing campaigns. Real banks do not send official communications via raw PHPMailer. Strong indicator.

Date: Timezone Analysis — تحليل التوقيتTimestamp Analysis

الرسالة أُرسِلت 06:23:38 UTC+0 ووصلت 09:23:39 UTC+3 — توقيت متزامن تقريباً. لكن الفارق بين Date: في الرسالة والـ Received: على الخادم يمكن أن يكشف تعديلاً مقصوداً للوقت. تحقق من التسلسل المنطقي: هل الـ Date قبل آخر Received؟Message sent at 06:23:38 UTC+0, received at 09:23:39 UTC+3 — roughly synchronized. However, discrepancies between the Date: in the message and the server Received: can reveal intentional time manipulation. Verify logical sequence: is Date before the last Received?
